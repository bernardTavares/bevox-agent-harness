# SDR Intelligence Module — Fase C Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Entregar a "máquina de vendas" do Ross executando: FSM Account Status + cadência como workflow durável, o elo de correlação Modelo-C-Híbrido (resposta inbound → resume da cadência suspensa certa, resposta governada pela doutrina com estado FSM no contexto, FSM avançada pós-resposta por guard determinístico), claims otimistas (race resume×cleanup), 2 migrations aditivas, o marcador de idempotência partida, e o wiring do tunável §7 — robusto e testado.

**Architecture:** O engine de workflow durável JÁ existe (`src/workflow/`). Fase C adiciona: migrations (`workflow_correlation` projeção + `workflow_executions.lock_version`); claims guardados (`claimForResume`/`claimForExpiry`) substituindo o `update` nu nas transições; extensão ADITIVA do payload dos hooks do engine (C-finding #1 — hooks não carregam accountId/contactKey); store de projeção de correlação mantido pelos hooks; sonda de correlação (passo 2.5) em `execution-handler`; a WorkflowDefinition FSM/cadência (lista plana de touches, guards determinísticos); o fluxo Modelo C (recompose com projeção FSM + advance pós-resposta awaited antes do ack); o marcador de idempotência partida (residual principal — desenhado, não deferido); e o wiring de `resolveQualificationFramework`.

**Tech Stack:** Node 20 / TS 5.9 ESM/NodeNext, Zod 4, Vitest 4, Postgres pgvector (testcontainers). Worktree `.claude/worktrees/sdr-impl`, branch `feat/sdr-intelligence-module`. Specs: `docs/superpowers/specs/2026-05-16-sdr-intelligence-module-design.md` §6 + `docs/superpowers/specs/2026-05-16-sdr-fase-c-correlation-bridge-design.md` (Modelo C DECIDIDO).

## C-findings / Landmines confirmados no código (LER PRIMEIRO — corrigem a spec)

- **CF1 (mais duro):** os hooks `onSuspended`/`onResumed`/`onWorkflowTerminal` (`src/workflow/engine.ts:127/216/241/284`) emitem APENAS `{executionId, workflowExecutionId, [suspendToken|status|resumeOn|timeoutAt]}` — **sem `accountId`, sem `contactKey`**. A afirmação da spec companheira §5/§2.3 "projeção mantida pelos hooks já emitidos, sem cirurgia em engine" é **FALSA**. **Decisão deste plano:** estender ADITIVAMENTE os 3 payloads de emit no engine para incluir `accountId` (em escopo via `opts.accountId`) e `contactKey` (lido de `opts.context` / `AgentExecutionContext.contactId`). É cirurgia mínima e aditiva no engine — desvio documentado da spec (CF1).
- **CF2:** `resolveQualificationFramework` (`src/sdr/tunables.ts:23`) é **dead code** (zero callers). `framework` hoje é escolhido pelo LLM em `qualify-opportunity/index.ts:215`, não determinístico. C9 conserta wrapando o `executeTool`.
- **CF3:** `resumeWorkflow` (`engine.ts:150`) hoje faz `update` incondicional e segue para `executeFrom`. Com claims guardados precisa **abortar quando `claimForResume` retorna 0 linhas** — mudança de comportamento no engine (desvio documentado; a spec §3 diz "resumeWorkflow inalterada" — verdade só p/ a assinatura, não o corpo).
- **CF4 (drift de linhas):** precedência de workflow = `execution-handler.ts:637-729` (não 607-612); pipeline span = linha 546 (não 519); session create 446-454; seam da sonda = **após linha 519, antes de 542**. Usar números atuais.
- **CF5:** `composeSystemPrompt`/`SdrAccountStateSnapshot` (`compose.ts:10-13`) só tem `{status,lastTouchAt}` — insuficiente p/ projeção FSM (Account Status + step de cadência + transições permitidas). C7 estende o snapshot/bloco.
- **L2:** dois runners de migration divergentes — `scripts/migrate.mjs` precisa de marker `-- UP` (senão roda o arquivo todo incl. DOWN); `integration-setup.ts` corta no `-- DOWN`. **Toda migration Fase C segue o padrão 008: SEM DDL executável após `-- DOWN` (bloco comentado de referência).**
- **L4:** o índice parcial-único de `workflow_correlation` precisa inlinar os literais de `resume_event` (predicado não referencia constante TS) — manter SQL ↔ constante TS `REPLY_RESUMABLE` em sincronia, testar ambos.
- **L5:** o builder (`src/workflow/builder.ts`) NÃO tem primitiva de loop; 7×7/9×15 deve ser lista PLANA de steps "touch" com ids únicos (`touch-1`,…); engine resume por cursor inteiro.
- **L6:** `tests/helpers/sdr-replay.ts` asserta contagem EXATA de system messages; qualquer system message extra (camada de projeção FSM) quebra a invariante — atualizar o helper no MESMO task (C7).
- **L7:** não existe evento `onCorrelationAmbiguity` no hook bus (`hooks/index.ts:7-12`) — adicionar à interface OU rotear via observability/logger; o plano usa o logger/observability como canal de alarme (mais simples, sem mexer no contrato do hook bus).
- **Nota:** `account_id` é BIGINT (migration 005) → `workflow_correlation.account_id` BIGINT. `contact_key` ← `agentContext.contactId` (bigint contact_id, consistente com a tabela `sdr_account_state` da Fase B); fall-through se ausente.
- **Residual principal (DESENHAR, não deferir):** idempotência partida sob retry — marcador "resposta-enviada" keyed `(account,contactKey,hash(msg))` separado de `harness:dedup:${execution_id}`. C8.
- **Residuais aceitos:** FIFO estrita por-contato (perdedor de race re-enfileirado, não dropado; ordem causal eventual); timing poll-driven (cleanup 5min); estabilidade do `contact_key` (dependência Bevox — assert presença, fall-through se ausente).
