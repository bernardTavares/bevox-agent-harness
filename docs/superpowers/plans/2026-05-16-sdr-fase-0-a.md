# SDR Intelligence Module — Fase 0 + Fase A Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Entregar a injeção de doutrina como mensagem `system` separada (Fase 0) e a faculdade cognitiva SDR — doutrina L0 gated por `sdr_profile`, ingestão de KB L1, e os 3 certification-gate scorers L5 (Fase A) — robusta e testada.

**Architecture:** O caminho vivo de execução resolve o system prompt do payload em `execution-handler.ts:470-471` e o **concatena no `input`** (`:725`), que vira `plan.goal` e é re-embrulhado por `buildSystemPrompt`. Fase 0 separa a doutrina num canal `system` dedicado via `AgentExecutionContext.systemPrompt` → `LlmCompletionRequest.doctrine` → `LlmClientBridge` emite uma system message líder. Fase A compõe a doutrina SDR no system prompt resolvido **apenas quando `agent_config.sdr_profile.enabled`** (gate determinístico, custo zero quando off), ingere a KB SDR via o CLI RAG existente (data-only), e adiciona 3 scorers ao `scorer-factory.ts` + um driver de fixture-replay pelo engine real.

**Tech Stack:** Node 20+, TypeScript 5.9 (ESM/NodeNext), Zod 4, Vitest 4. Worktree: `.claude/worktrees/sdr-impl`, branch `feat/sdr-intelligence-module`. Specs: `docs/superpowers/specs/2026-05-16-sdr-intelligence-module-design.md` (§3 Fase 0, §4 Fase A).

## Contradições da spec confirmadas no código (LER PRIMEIRO — reformulam o plano)

- **C1** — `ContextBuilder`/`BaseConfigLayer` **não estão no hot path** (nada instancia `ContextBuilder` em `src/` não-teste). O systemPrompt vivo é `agentConfigRaw["system_prompt"]` em `execution-handler.ts:470-471`. **A doutrina L0 da Fase A é composta nesse ponto, não na `BaseConfigLayer`.** Editar só `BaseConfigLayer` = teste verde + zero efeito runtime (armadilha de no-op silencioso).
- **C2** — A doutrina não é degradada por truncamento hoje (não há compressão no caminho vivo); o defeito é puramente de **canal de role** (concatenada no `goal`). O critério §3.4 (sentinela no canal `system` separado, não no `goal`) continua certo e não-trivial.
- **C3** — O array `traces` (`execution-handler.ts:728`) é **morto** (nunca lido/enviado). A observabilidade §3.3 é satisfeita asserindo direto no objeto-evento do `TraceCallback` no teste (padrão `react.test.ts:84-94`).
- **C4** — `agent_config` é `z.record(z.string(), z.unknown())` aberto. `sdr_profile` é lido ad-hoc como `agentConfigRaw["sdr_profile"]`, validado por um `sdrProfileSchema` dedicado (não reescrever o record).
- **§4.3/§4.4 "registry.ts"** — registro de scorer é em **`src/evals/scorer-factory.ts`** (switch por nome), não `registry.ts` (só singletons de enabled-list).
- **§4.3 "replay pelo engine real"** — esse harness **não existe**; Task A.8 o constrói (driver de teste; sem mudança em `src/`).
- **§3.2 "não editar 4 engines"** — atingível para a *lógica de construção de prompt*; cada engine precisa de 1 linha de pass-through `doctrine: context.systemPrompt`. **Fase 0 aceita verde só no ReAct** (default de surface agent por `strategy-router.ts:92`); os outros 3 engines = uma task de consistência (0.6).

import { SDR_DOCTRINE } from "./doctrine.js";
